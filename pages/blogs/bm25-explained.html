BM25, explained through this site's search box

How BM25 scores a document, term by term: saturation with k1, length normalisation with b, a never-negative IDF, and a worked example by hand.

The search box on this site (press / or Ctrl+K) ranks every page, tool, paper and post with BM25, using the parameters k1=1.2k_1 = 1.2k1​=1.2 and b=0.75b = 0.75b=0.75. The index is built at deploy time from page titles, descriptions and headings, and a match in a title counts for more than a match elsewhere. This note explains what BM25 computes, why each part of the formula is there, and then works through a tiny example by hand so that every number can be checked.

#What a ranking function has to do

A query is a handful of words. The collection is a set of documents. A ranking function gives each document a number, and the search box shows documents in decreasing order of that number. BM25 belongs to the "bag of words" family: it ignores word order and looks only at which query terms appear in a document and how often.

Three intuitions drive the formula:

  1. A document that mentions a query term more often is more likely to be about it, but the tenth mention adds much less than the first.
  2. A rare term is more informative than a common one. Matching "molecule" says more than matching "the".
  3. One mention in a short document is stronger evidence than one mention in a long document.

BM25 turns each intuition into one factor. Robertson and Zaragoza's monograph on the probabilistic relevance framework derives these factors in detail [1]; what follows is the working version.

#Term frequency saturation: what k1k_1k1​ controls

Look at the fraction f (k1+1)f+K\dfrac{f\,(k_1+1)}{f + K}f+Kf(k1​+1)​ as a function of fff. #Length normalisation: what bbb controls

Inside K(D)K(D)K(D), the ratio ∣D∣/avgdl|D| / \mathrm{avgdl}∣D∣/avgdl compares the document's length with the average. The parameter bbb decides how much that comparison matters:

  • b=0b = 0b=0: K=k1K = k_1K=k1​ for every document. Length is ignored.
  • b=1b = 1b=1: K=k1⋅∣D∣/avgdlK = k_1 \cdot |D| / \mathrm{avgdl}K=k1​⋅∣D∣/avgdl. Term counts are judged fully relative to length.
  • b=0.75b = 0.75b=0.75, the usual default, sits between the two.

A longer document gets a larger KKK, which lowers the term-frequency fraction for the same count. Robertson and Zaragoza describe two reasons a document can be long [1]: it may say the same things at greater length (verbosity), in which case its counts should be scaled down, or it may cover more ground (scope), in which case its counts are genuine evidence. A value of bbb below 1 is a compromise between those two views.

#Inverse document frequency, and why the +1+1+1

Let NNN be the number of documents and n(q)n(q)n(q) the number of documents containing term qqq. The classic Robertson/Spärck Jones weight, in the case where nothing is known about which documents are relevant, is [2]:

IDF⁡RSJ(q)=log⁡N−n(q)+0.5n(q)+0.5\operatorname{IDF}_{\mathrm{RSJ}}(q) = \log \frac{N - n(q) + 0.5}{n(q) + 0.5}IDFRSJ​(q)=logn(q)+0.5N−n(q)+0.5​

It rewards rare terms, which goes back to Spärck Jones's observation that a term's value for retrieval falls as it is shared by more documents [3]. It has one awkward property: when a term appears in more than half the documents, the fraction drops below 1 and the logarithm goes negative. A document would then be penalised for containing a query word, and would score below a document that matches nothing at all.

Apache Lucene, the library underneath Elasticsearch and Solr, adds 1 inside the logarithm [4]:

IDF⁡(q)=log⁡(1+N−n(q)+0.5n(q)+0.5)=log⁡N+1n(q)+0.5\operatorname{IDF}(q) = \log\left(1 + \frac{N - n(q) + 0.5}{n(q) + 0.5}\right) = \log \frac{N + 1}{n(q) + 0.5}IDF(q)=log(1+n(q)+0.5N−n(q)+0.5​)=logn(q)+0.5N+1​

The second form shows why this can never be negative: n(q)≤Nn(q) \le Nn(q)≤N, so N+1>n(q)+0.5N + 1 > n(q) + 0.5N+1>n(q)+0.5 and the argument of the logarithm is always greater than 1. Rare terms still get large weights; a term found in every document gets a small positive weight instead of a large negative one. The logarithm here is natural.

Each intuition from the start shows up in these numbers:

  • Rarity. D1 wins because it is the only document with "molecule", the term with the larger IDF. That single match contributes 1.3061 of its 1.4839.
  • Saturation. D2 says "viewer" three times. A single mention in a document of D2's length would give a fraction of 1.0369; three mentions give 1.6013, about 1.5 times as much rather than three times. D2 still scores less than a sixth of D1.
  • Length. D1 and D3 each contain "viewer" once, but D1 is 3 tokens long and D3 is 13, so D1's "viewer" contribution is 0.1778 against D3's 0.1039. With b=0b = 0b=0 the length penalty disappears and D3 rises to 0.1335; with b=1b = 1b=1 it falls further, to 0.0968.

Now repeat the sums with the classic IDF and no +1+1+1. The scores become −1.911-1.911−1.911 for D1, −3.116-3.116−3.116 for D2 and −1.515-1.515−1.515 for D3. The order flips: D3 now ranks first, D2 is last because it mentions "viewer" most often, and an empty document scoring 0 would beat all three. This is the failure the +1+1+1 is there to prevent.

The same calculation in Python, which prints the three totals in the first column of the last table:

import math
import re

docs = {
    "D1": "interactive molecule viewer",
    "D2": "pdf viewer, image viewer and audio viewer",
    "D3": "notes on building a fast viewer for large research papers in the browser",
}

def tokenize(text):
    return re.findall(r"[a-z0-9]+", text.lower())

tokens = {name: tokenize(text) for name, text in docs.items()}
N = len(tokens)
avgdl = sum(len(t) for t in tokens.values()) / N

def idf(term):
    n = sum(1 for t in tokens.values() if term in t)
    return math.log(1 + (N - n + 0.5) / (n + 0.5))

def bm25(query, doc, k1=1.2, b=0.75):
    t = tokens[doc]
    K = k1 * (1 - b + b * len(t) / avgdl)
    score = 0.0
    for term in tokenize(query):
        f = t.count(term)
        score += idf(term) * f * (k1 + 1) / (f + K)
    return score

for doc in tokens:
    print(doc, round(bm25("molecule viewer", doc), 4))
# D1 1.4839
# D2 0.2138
# D3 0.1039

#What this means for the search box

On this site the "documents" are pages, tools, papers and posts, and the text that gets indexed is their titles, descriptions and headings. Some entries have a one-line description and others have many headings, so their indexed text varies a lot in length. Length normalisation keeps a short entry that mentions your query word once from losing to a long entry that mentions it once in passing. The values k1=1.2k_1 = 1.2k1​=1.2 and b=0.75b = 0.75b=0.75 are the same defaults Lucene ships with [4].

The reasoning behind weighting titles higher is that a word in a title is usually a direct statement of what the page is about, while a word in a heading or description may be incidental. Robertson and Zaragoza also describe BM25F, an extension of the formula for documents made of several fields with different weights [1], which treats that idea formally.

#What BM25 cannot do

BM25 only rewards exact term overlap. If you type "protein structure" and a page says "fold", BM25 sees no match. It also ignores order, so "dog bites man" and "man bites dog" score the same. These limits are why retrieval systems often add dense embeddings, which compare meanings rather than surface words. The next article in this series, on hybrid search with reciprocal rank fusion, shows one way to combine the two. The article on our TREC Tip-of-the-Tongue work shows a different fix: keep BM25, and rewrite the query so that it uses the words the target document is likely to contain.
